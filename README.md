# DataBNB

DataBNB is a local-first workspace for importing and exploring structured data. Start with CSV and Excel files, search and filter the full dataset, adjust a table view, inspect and edit records, and export a filtered result. Imported data and saved views stay in a local DuckDB database.

## Current features

- CSV and XLSX preview and import, including workbook worksheet selection, duplicate-header normalization, UTF-8/Windows-1252 CSV decoding, and basic type inference for text, numbers, booleans, and ISO dates.
- DuckDB persistence, stable dataset and record IDs, dataset metadata, and an import limit of 25 MB, 100,000 rows, 200 columns, and 2,000,000 cells.
- Server-side search, sorting, pagination, nested AND/OR filter definitions, text/numeric/date/boolean comparisons, and safe CSV/XLSX exports of all matching rows and selected visible columns.
- Record inspection, creation, editing, and deletion.
- Saved filter, table-view, and record-detail configurations. Filter and table views support update, save-as-new, and delete. Table views preserve visible columns, their order, and sort order. Detail views allow field selection/reordering, labels, and a one- or two-column presentation. The selected dataset and saved views are remembered in the local browser.
- Responsive React/TypeScript workspace with keyboard-focusable controls and loading, empty, and error states.

Spreadsheet imports are local copies. Database/API connectors, joins, date-relative filters, nested filter-group editing in the UI, column resizing, concurrent multi-user writes, and advanced multi-section detail layouts are not implemented.

## Architecture

- **`backend/`** — FastAPI request validation and routes, spreadsheet decoding, structured filter compilation, and DuckDB-backed persistence.
- **`frontend/`** — React and TypeScript UI, Vite development server, and browser API client.
- **`data/databnb.duckdb`** — Default local database path. Set `DATABNB_DATABASE_PATH` to store it elsewhere.

The database keeps dataset/configuration metadata separate from each dataset's generated physical table. Internal table and column identifiers are generated by the application; uploaded column names are stored as display metadata. User filter values are bound SQL parameters. Configuration records include a schema version for future migrations.

## Requirements

- Windows 10/11 with Python 3.11 or newer.
- Node.js 20.19+ or 22.12+ and npm.
- Git (optional, for source control).

## Start on Windows (PowerShell)

From the repository directory, create and activate a virtual environment and install backend dependencies:

```powershell
py -3.12 -m venv .venv
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -r backend\requirements.txt
```

Start the API in this PowerShell window:

```powershell
python -m uvicorn backend.app.main:app --reload --host 127.0.0.1 --port 8000
```

In a second PowerShell window, install and start the frontend:

```powershell
cd frontend
npm install
npm run dev
```

Open the local URL printed by Vite (normally `http://localhost:5173`). The API is available at `http://127.0.0.1:8000`; interactive API documentation is at `http://127.0.0.1:8000/docs`.

To use a non-default API URL, set `VITE_API_URL` in `frontend/.env.local` (for example, `VITE_API_URL=http://127.0.0.1:8000/api`). To relocate the database, set `DATABNB_DATABASE_PATH` in the API process environment before starting Uvicorn. `.env.example` lists these optional settings; environment files are not loaded automatically by the backend.

## Development and tests

Run backend tests from the repository root:

```powershell
python -m pytest backend\tests -q
```

Run frontend linting and a production build from `frontend`:

```powershell
npm run lint
npm run build
```

The build command also runs the TypeScript project checks. The frontend currently uses the available lint/build checks; no separate UI test runner is configured.

## Storage, backup, and limitations

The default database is created at `data/databnb.duckdb`; source uploads are read in memory and are not copied into an uploads directory. Back up the database while the application is stopped by copying the database file to a protected location. Do not delete or replace it unless you intend to remove the imported datasets and saved configurations.

This is a single-user local application. DuckDB is embedded in the API process and is not a multi-user database server; run one API process and avoid concurrent external writers. Data is stored without encryption at rest. Uploaded files and data are not sent to a cloud service by the application. Anyone with access to the local account or database file can read its contents. Keep sensitive files out of shared or untrusted computers.

## Roadmap

Potential future work includes more source connectors, richer group editing and date operators, saved default views, drag-and-drop column ordering, advanced detail sections, and derived datasets and joins.
